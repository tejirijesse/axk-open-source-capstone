1. Problem and approach

Cross-border agricultural trade between Rwanda, the DRC and Uganda fails at two points: a buyer cannot verify a lot's quality, custody and container integrity along the corridor, and settlement is slow and hard to trust. This project puts both in one workflow. A cooperative registers a lot, an independent inspector signs it off on-chain, a buyer locks payment in escrow, a carrier records dispatch under a container seal, the port checks the seal and records clearance, and on delivery confirmation the contracts release payment, split it 40/40/20 between members and write an attestation anyone can check through a QR code. Four Soroban contracts (lot registry, escrow, splitter, attestation) hold the rules; a Frappe v15 app holds the roles, screens and signing.

Each of the six trade steps is one HTTP call from a role screen to a whitelisted function in trade_api.py. The function checks the login and role, calls the matching function in chain.py, which builds the canonical record, hashes it, invokes the contract and stores the transaction hash on the AXK Chain Trade document. If the chain call fails, the step fails and nothing is recorded, so the database never claims something the ledger did not accept. Reads for the public pages come from the stored hashes, re-checked against the contracts by matches_on_chain, and the browser re-hashes the records itself.

3.1 Controls on the application layer

  • Access guard: _guard() in trade_api.py allows a signed-in user with the AXK Capstone Demo role (or System Manager). Demo mode (axk_demo_mode) only works for requests made directly on loopback; anything through a proxy is refused. The hosted site runs with demo mode off.
  • Throttle: _throttle() caps 30 signed transactions per user per hour, keyed by user and not by IP, so a shared reviewer login cannot spam testnet.
  • Keys: per-role Stellar identities live on the server under the service user (directory 700, files 600, outside git). The browser never holds a key. See docs/handover.md and docs/security.md.
  • Privacy: verify.py exposes a fixed list of PII-free fields to the public trace page.

3.2 Two ways to run it

Full stack (make run-frappe): every action is a real Stellar testnet transaction; this is what capstone.axk.org and the demo video show. Offline simulation (make run, scripts/server.py, Python only): the same screens with locally generated hashes, labelled "Offline simulation, not on-chain" on every page and never linked to a block explorer. It exists so the screens can be tried and the end-to-end tests run without a bench.

3.3 What was exercised on testnet

docs/deployments.md records a run of scripts/demo.sh on 29 September 2026 with the contract IDs, transaction links and the exact errors the contracts returned: funding before inspection gives Error(Contract, #10) LotNotApproved; a cooperative inspecting its own lot gives #3 NotAnInspector; a second escrow on a sold lot gives #11 LotInEscrow; a stranger calling release is refused.

3.4 Standards and interoperability

Every lot's public history exports as a GS1 EPCIS 2.0 document (epcis.py, validated against the official schema when jsonschema is installed). Inspections captured offline in ODK are imported through odk.py and signed on import.

4.1 Failure-mode tests (money and integrity paths)

Because escrow and settlement move value, failure paths were written before happy-path polish. Examples from the contract suite, in contracts/*/src/test.rs:

#[test]

#[test]
fn an_unknown_trade_id_is_an_error_not_a_panic() { /* escrow and splitter */ }

The end-to-end suite adds the application side: a rejected lot cannot be funded, a container arriving with a different seal than the waybill is flagged and blocked, a buyer cannot confirm delivery before dispatch, and a lot that was never registered returns an error with no state change. On Stellar testnet the same refusals were observed as real contract errors (section 3.3).

4.2 What testing does not cover

The end-to-end tests ran here against the offline simulation; against the full stack each step is a testnet transaction and takes seconds, so that run is done by hand (make demo, the demo video). There is no load test, no browser-automation suite and no external audit of the contracts.

The screens use no frontend framework and no chart library (SVG is hand-built), so the heaviest page ships about 32 KB of gzipped assets. Against the offline simulation on a laptop, /trade, /trace and /chain each returned in about 1 ms (2.4 KB, 5.3 KB and 6.6 KB gzipped HTML). Records are re-hashed in the browser with the WebCrypto SHA-256 API. These are server-side local figures, not field measurements over 3G; no mobile-network test was run.

On the full stack the time is dominated by Stellar: each action is a signed transaction submitted through stellar-cli and confirmed in a ledger close, which takes a few seconds on testnet (not benchmarked here). The signer therefore runs a call with a 90 second timeout and reports a clear "Stellar testnet did not answer in time" error instead of hanging. Wallet balances are cached (forget_balances clears them after a payment) so role screens open without a chain read per row. The chain explorer reads events from Soroban RPC, which only keeps about 7 days of history; the pilot plan adds an indexer for that.

5.2 Browser compatibility

The front end is plain HTML, CSS and JavaScript with fetch, inline SVG and WebCrypto, all of which are available in current Chrome, Edge, Firefox and Safari, and in mobile Chrome and Safari. The responsive layout targets phones used by cooperative and field staff. No formal cross-browser test matrix was run, and I do not claim one. One known quirk is recorded in the README: Safari does not resolve *.localhost, so local use needs http://localhost:8000.

5.3 Deployment and platform

Tested on macOS 15 (Apple silicon) with Homebrew, and on the hosted Ubuntu 24.04 VM (nginx, supervisor, Frappe v15, MariaDB 10.11, Redis) at capstone.axk.org. Tool versions: Rust stable with target wasm32v1-none, soroban-sdk 22, stellar-cli 28, Python 3.11. The hosted site has demo mode off and requires a login to sign. 6. Code quality and object-oriented design

The code base is about 2,300 lines across the four contracts and the Frappe app modules, with no module doing two jobs. The object-oriented structure sits in three places: the contracts, the Frappe document model, and the layering between them.

6.1 Contracts: types, encapsulation, typed errors

Contract and fileTypesDesign point
contracts/lot_registry/src/lib.rsLotRegistry (contract), Lot, Inspection (structs), LotStatus (enum), ErrorState is private to the contract; the only way to change a Lot is a method that checks the caller. Status moves forward only.
contracts/escrow/src/lib.rsEscrow contract, trade record, Error with 10 named codes (LotNotApproved = 10, LotInEscrow = 11)Depends on the registry only through its client interface (cross-contract call), so the two evolve separately.
contracts/splitter/src/lib.rsSplitter contract, Share struct (party, basis points), ErrorShares are fixed per trade at configuration time and cannot be edited afterwards.
contracts/attestation/src/lib.rsRegistry contract, Attestation struct, ErrorWrite-once digest per trade; only the attester can write.

Failures are values, not panics: each contract defines a #[contracterror] enum, and chain.py maps the numeric code back to a readable message (CONTRACT_ERRORS), so an operator sees "lot not approved" rather than "Error(Contract, #10)".

6.2 Application: model, service layer, boundary

  • Model: AXKChainTrade(Document) in frappe_app/axk_capstone/axk_capstone/axk_capstone/doctype/axk_chain_trade/axk_chain_trade.py is the persistent record of one trade (79 fields: lot record and digest, report digest, one transaction hash per on-chain step). Permissions and field rules are declared in its JSON schema.
  • Service layer: chain.py exposes one function per trade step (register_lot, inspect_lot, fund_escrow, dispatch_logistics, receive_port, settle) that takes the document and updates it. All process execution is behind a single private function _run, so the transport (stellar-cli today) is replaceable in one place. ChainError is the single exception type crossing the boundary; _fail in trade_api.py records it on the document.
  • Boundary: trade_api.py holds only whitelisted endpoints plus _guard and _throttle; it contains no contract details. verify.py, epcis.py and odk.py each own one concern (public lookup, standards export, offline import).

I am not claiming a Strategy or Repository class hierarchy: the Python side is a thin service module around one Document class and one exception class, which is the idiomatic Frappe shape. The inheritance and encapsulation come from the Frappe Document base and from the Soroban contract types.

6.3 Algorithms worth reading

Canonical digest (chain.py)
def canonical(obj):
    return json.dumps(obj, sort_keys=True,
        separators=(",", ":"), ensure_ascii=False)
def sha256_hex(text):
    return hashlib.sha256(text.encode("utf-8")).hexdigest()
Sorted keys and no whitespace make the same record hash the same in Python, in the browser re-check and in the EPCIS export.
Lossless split (splitter)
let part = if i as u32 == last {
    amount - paid          // remainder
} else {
    amount * share.bps / BPS
};
paid += part;
Integer division truncates; the last share receives what is left, so the parts always add up to the amount paid in.
