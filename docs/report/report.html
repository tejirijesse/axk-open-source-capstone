AXK Network: a Verification-and-Settlement Layer for Cross-Border Agricultural Trade

Final version of the product, technical report. Oghenetejiri Jesse, BSE Software Engineering (Low-Level / Blockchain), African Leadership University. Supervisor: Junior Turatsinze. October 2026.
Repository: github.com/tejirijesse/axk-open-source-capstone (release v0.1.0, MIT). Walkthrough video: youtu.be/MrSXiJG_MAU. Public demo (offline simulation): axk-open-source-capstone.vercel.app.

1. Overview

Cross-border agricultural trade around Kigali fails at two points: a buyer across the border cannot verify a lot's quality, quantity and origin, and payment is slow and hard to trust. AXK Network puts verification and settlement in one workflow. A cooperative registers a lot; an independent inspector signs it off; the buyer's payment is held in a smart-contract escrow that only accepts inspected lots and can only pay the cooperative that registered the lot; a carrier and a port record custody; on delivery the escrow releases, the payment is split between cooperative members and the whole trade is attested. Every step is a Stellar testnet transaction, and anyone can check a lot's history on a public page or by scanning its QR code, without an account.

Justification of changes. (1) Stack. The proposal suggested React, Node.js and PostgreSQL. The product uses Frappe (Python, MariaDB) because it provides role permissions, a REST layer, a database and an admin interface out of the box and matches AXK's existing platform, which left the effort for the trust-critical parts; the "distributed ledger" became Stellar Soroban for its low fees, native local-currency assets and multi-party authorisation. (2) Mobile app to responsive web. A web app needs no installation and runs in any phone browser; offline field capture is covered by ODK instead. (3) Logistics and port roles were added because the design showed a custody gap between payment and delivery. (4) No accounts for verification is deliberate: anyone can check a lot, and no personal data is shown. (5) The pilot depends on ethics approval, which is in review; all instruments are prepared.

3. Technical functionality

3.1 Architecture and data handling

Four layers, as in the proposal (Fig. 2 of the proposal): presentation (Frappe web pages and vanilla JavaScript, www/, public/js/trade.js); application (REST endpoints in trade_api.py with an access guard and a per-user rate limit, and the object-oriented ledger package); data and trust (MariaDB for application records, four Soroban contracts for trust-critical state); external (Soroban RPC and Horizon; ODK Central; GS1 EPCIS consumers). The browser calls /api/method/axk_capstone.trade_api.* with JSON; the server builds the step's record, signs through stellar-cli with an argument list (never a shell string), stores the transaction hash, and returns the updated trade. Each record (lot, inspection report, waybill, port receipt, settlement) is serialised as canonical JSON and hashed with SHA-256; only the 64-character digest goes on-chain. Names, notes and farmer data stay off-chain, and the public page shows statuses, digests and transaction hashes only. The browser can re-hash a record with Web Crypto and ask the contract whether it still matches.

4.2 Improvements made from test results

  • Logistics and Port screens took 66 s to open: balance look-ups for accounts that hold no token failed slowly and were not cached. Now only token holders are queried and results are cached: 1.4 s.
  • The simulation server answered unknown URLs with files from the repository, which could expose local configuration. It now returns 404.
  • Logistics and port steps once recorded a placeholder hash when the chain call failed. Removed: a failed transaction now fails the step.
  • The public deployment returned 404 for every page because the host rewrote the path; and browsers kept old scripts after a deploy. Fixed with path restoration and content-hash asset versions.
  • On the slow-phone profile the first page took 57.7 s: every screen loaded 3.9 MB of framework bundles it never used. A lean page template now loads only each screen's own CSS and JavaScript (about 2.6 KB of HTML per page); the slowest low-end load fell to 2.7 s.
  • The live chain page broke when the Stellar testnet RPC changed its event format, which the SDK's strict parser rejected. It now reads events over plain JSON-RPC, keeping only the fields it uses.
  • The blockchain module was one procedural file; it was restructured into classes (section 5) with 21 unit tests, and verified by a full testnet trade.

5. Code quality and engineering practice

PrincipleHow it is applied
EncapsulationContractClient hides how a contract call is built and how errors are read; callers use typed methods such as Escrow.create() or LotRegistry.inspect(). Smart contracts keep state private behind their public functions.
AbstractionAbstract base classes CommandRunner (how commands run) and CanonicalRecord / AttestedRecord (what a record must provide).
InheritanceLotRegistry, Escrow, Splitter, Attestation, Token extend ContractClient; LotRecord, InspectionReport, Waybill, PortReceipt, SettlementRecord extend the record base classes.
PolymorphismEach record class answers attestation_key() its own way, so verification loops over records without knowing their type; each contract client has its own ERRORS table; StellarCli and the test runner are interchangeable.
SOLID / separation of concernsThe ledger package has no web-framework dependency (single responsibility, dependency inversion): configuration, clock, cache and saving are injected by chain.py. New contracts or record types are added by subclassing (open/closed).
Modularity and organisationcontracts/ (one crate per contract), frappe_app/.../ledger, trade_api.py (HTTP), verify.py (public data), epcis.py, odk.py, www/, public/, scripts/ (tests and tools), docs/.
Readability and maintenanceDescriptive names (a_cooperative_cannot_inspect_its_own_lot), module docstrings explaining why, a Makefile with one command per task, make check-env, contribution guide, security policy and roadmap. History of meaningful commits on GitHub.
Security by designNo shell strings, argument lists only; personal data never on-chain; access guard and rate limit on signing; write-once records; 14 guarantees each tested.

6. Limitations and next steps

Keys are held by the server for each role (custodial) and the carrier's and port's attestations are signed by the verifier on their behalf; non-custodial signing (roadmap BUY-3, LOG-4) is the next step before any real money. The system runs on testnet only; the contracts are not audited. The pilot (objective 4) starts after ethics approval, using the questionnaire and interview instruments already prepared. Mobile-money payout (SET-2, SET-3) and translation into Kinyarwanda, French and Swahili (I18N-1) are planned.
